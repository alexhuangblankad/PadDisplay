v0.1.6: 分辨率/显示模式诊断增强，不再靠"没报错"当成功

## 从用户日志读出的硬事实

- 外接屏(displayId=13) windowingMode: FULLSCREEN(1)
  → 已经是扩展模式，不是镜像。"镜像导致改不了分辨率"的假设是错的。
- getWindowingMode code: 98 / setWindowingMode code: 99
  → 修正后的 code 在设备上真的执行了。
- 外屏是 4K 屏（型号 OPD2515），当前就跑在 3840x2160@60。
- 日志里那次"切换"的目标是 3840x2160@60，与外屏当前模式完全一样
  → 那次调用本来就是空操作，不是失败。

这暴露了一个工具性缺陷：无法验证"换一个分辨率到底行不行"。

## 本版修复

1. Mode 切换现在会「读回验证」。
   RESULT_OK=true 只代表调用没抛异常，不代表分辨率真的变了。
   现在每次切换后都 getUserPreferredDisplayMode() 读回比对：
   调用成功+读回一致=成功；调用成功+读回不一致=请求未被系统采用（明确报告）；
   调用失败=附完整异常。

2. 目标与当前相同 -> 明确告知"已经是 X，无需切换"，
   并提示要验证能否切换请选另一个分辨率。

3. 新增「Mode 自检」按钮，一键输出：
   App 侧当前 Mode / supportedModes 数量 / 可选分辨率、
   UserService 侧读回的真实 Mode / 用户首选 Mode / 系统首选 Mode、shell 环境。

4. 修掉 shell 命令可能静默失败的问题。
   wm / dumpsys 在 /system/bin 下，但 Shizuku UserService 进程的 PATH 不一定包含它。
   早先用 sh -c "wm size -d N" 可能失败且无输出，导致读到空字符串、
   快照变 0x0、回滚机制失效。现在显式补全 PATH 并返回退出码。

5. 修掉一个状态竞态：applyBestResolution() 原来先改 UI 状态再立刻读状态，
   可能读到旧值，导致"最佳分辨率"实际没被应用。现在改为显式传参。

6. 分辨率列表标出「← 当前」，并在只有一种分辨率时明确说明没得选。

## 关于复制/扩展的诚实说明

- 「扩展」可实现：per-display 设独立 FULLSCREEN，并读回 getWindowingMode 验证。
- 「复制」本应用不强制切换：Android 14 起已移除强制镜像 API
  （setDisplayIdToMirror 在 API 34/35/36 的 AIDL 里都不存在）。
  硬做需要改 display 的 enable 状态，有让内屏一并熄灭的风险。

## 验证步骤

1. 点「Mode 自检」，把报告发回
2. 看分辨率列表里除了 4K@60 还有没有别的
3. 选一个不同的分辨率（如 1920x1080）→ 点应用
4. 看事件日志里「读回验证(首选 Mode)」那一行：
   系统已接受 = 通道有效；请求未被系统采用 = 通道被 ColorOS 挡了，改用逻辑尺寸通道
