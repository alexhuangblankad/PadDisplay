v0.3.2: 光标错位的根因（坐标空间被应用缩放污染）+ 坐标空间对照工具

## 根因类别定位

参考项目 AdaptiveScreenPlus 的 CursorOverlay / ExtScreen 里踩透并写成了警告：
- 范围必须从系统那一侧量，不能问 Display：display context 的
  getResources().getDisplayMetrics() 会被本应用的兼容缩放污染 ——
  实测内屏 1920x1080 被报成 1496x1242，光标被夹在 x<=1495，右侧 424px 够不到。
- Display 的 getRealSize/getMetrics 会串应用缩放，getMode() 又不认 wm size 覆盖。
- 系统只给真实鼠标（USB/uinput）画指针，应用侧注入的事件不会点亮它，
  非 root 没有接口，只能自己挂应用悬浮窗当光标。

所以用户的现象是两类问题叠加：
1. 坐标空间取错源：事件按一套空间算、光标按另一套画；两块屏尺度不同（内屏
   2520x1680 / 外屏 3840x2160）误差被放大，表现为"飘逸"。
2. 物理鼠标绑定让错位更明显：系统把指针画在默认屏，事件却被绑到外屏。

## 本版改动

1. 新增「对照坐标空间」：解析 dumpsys window displays 里每块屏的 cur=WxH
   （WindowManager 眼里的逻辑尺寸，已算上旋转与 wm size 覆盖，
   与 input -d N tap x y / screencap 同一套坐标系），
   并把 Display.getRealSize()/getMetrics() 的读数并排显示以暴露污染。
2. 新增「外屏注入点击」：按 cur=WxH 空间注入点击，坐标自动夹取并告知是否夹取。
3. 新增 CoordinateSpaceProbe.kt 实现上述解析与注入。

## 三个参考项目的结论

- connect-screen：从 android-display-extend 派生，用虚拟显示器（非物理便携屏）。
- SmartDock DFC：前置桌面 + 强制桌面模式，提供桌面外观但不解决输入坐标。
- AdaptiveScreenPlus：自挂光标浮层 + 注入事件到目标屏，坐标取自
  dumpsys window displays —— 这才是正确架构。

结论：非 root 下要让第二块屏能用，不是去绑物理鼠标，而是自己画光标 + 自己注入事件。

## 请先做这一步

先点「解除绑定」清掉鼠标绑定（鼠标飘逸应该是它引起的），再看坐标空间对照输出。

## 下一步需要的数据

1. 解除绑定后鼠标飘逸是否消失
2. 坐标空间对照输出（两块屏的 cur=WxH）
3. 输入设备列表里 external=true 的设备

拿到 cur=WxH 即可判断是坐标空间取错，还是 ColorOS 的指针绘制与输入空间本就分离。
若是后者，按 AdaptiveScreenPlus 的路子做「自绘光标 + 注入」的触控板，不再碰物理绑定。
