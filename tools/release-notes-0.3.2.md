v0.3.2: 光标错位的根因（坐标空间被应用缩放污染）+ 坐标空间对照工具

## 你的「鼠标飘逸」找到了根因类别

参考项目 [AdaptiveScreenPlus](https://github.com/PyMakesMeProud/AdaptiveScreenPlus) 的
`CursorOverlay` / `ExtScreen` 里把这件事踩透并写成了警告，我原文引一下：

> ⚠ **范围（bounds）必须从系统那一侧量，不能问 Display**：
> display context 的 `getResources().getDisplayMetrics()` 会被**本应用的兼容缩放**污染 ——
> 实测内屏明明是 1920×1080，它报 1496×1242，于是光标被夹在 x≤1495，
> **右边 424px 永远够不到**（用户报的「光标到不了最右边」）。
>
> ⚠ Display 的那几个 API 都别用：`getRealSize/getMetrics` 会串应用缩放，
> `getMode()` 又不认 `wm size` 覆盖。

同一份注释还解释了另一个关键点：

> **系统只给真实鼠标（USB / uinput）画指针，应用侧注入的事件不会点亮它**，
> 非 root 没有接口 —— 只能自己挂一层应用悬浮窗当光标。

**所以你的现象是两类问题叠加：**

1. **坐标空间取错了源**。事件按一套空间算、光标按另一套空间画，
   两块屏（内屏 2520×1680 / 外屏 3840×2160）尺度又不同，误差被放大 → 「飘逸」。
2. **物理鼠标绑定让错位更明显**。系统把指针画在默认屏上，
   而事件被我们绑到了外屏 —— 这本身就会造成"看得见的光标"和"实际点击点"分离。

## 本版做了什么

### 1. 把可靠的坐标空间测出来（新工具）

新增 **⑧ 对照坐标空间**：直接解析 `dumpsys window displays` 里每块屏的
**`cur=WxH`** —— 这是 WindowManager 眼里的逻辑尺寸，已算上旋转与 `wm size` 覆盖，
并且与 `input -d N tap x y`、`screencap` **是同一套坐标系**。

同时把 `Display.getRealSize()` / `getMetrics()` 的读数**并排显示**，
让"被污染"这件事一眼可见。

### 2. 注入点击验证

**⑧ 外屏注入点击**：按 `cur=WxH` 空间把点击注入到外屏中心，
坐标会自动夹取到有效范围（并明确告知是否发生了夹取）。
用来验证坐标空间是否对齐。

## 关于"重新再试"的路线调整

我把你给的三个项目都读了，结论如下：

| 项目 | 做法 | 对我们意味着什么 |
|---|---|---|
| [connect-screen](https://gitee.com/connect-screen/connect-screen) | 从 android-display-extend 派生，**用虚拟显示器** | 虚拟屏不是你要的（你要物理便携屏） |
| SmartDock DFC | 前置桌面 + 强制桌面模式 | 提供"桌面"外观，不解决输入坐标 |
| [AdaptiveScreenPlus](https://github.com/PyMakesMeProud/AdaptiveScreenPlus) | **自挂光标浮层 + 注入事件到目标屏**，坐标取自 `dumpsys window displays` | **这才是正解**，坐标空间与光标都要自己维护 |

**AdaptiveScreenPlus 的架构说明了一件事**：在非 root 下要让第二块屏"能用"，
**不是去绑物理鼠标**，而是「**自己画光标 + 自己注入事件**」。
它宁可起一个触控板页面用注入的方式控制副屏，也不走物理设备绑定那条路 ——
因为物理绑定在多数 ROM 上就是会错位。
